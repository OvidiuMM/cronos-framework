# Cronos Framework — Proposed Amendments (v2.1)

**Status:** Proposal
**Author:** Ovi
**Date:** 2026-07-11
**Evidence base:** Cycle retros 0001-text-to-pay-rework, 0002-aich-dashone, 0003-universal-ai, 0009-salesforce-milestone-sync (plus the unfilled 0004 retro as negative evidence).

Each amendment cites the cycle(s) that motivated it. Amendments backed by two or more independent cycles are marked **[recurred]** — under the framework's own 3-cycle promotion logic, these have earned rule status rather than lesson status.

---

## A1 — Cycle Chaining Limit (new Mandate 4)

**Rule:** No person runs more than **3 consecutive delivery cycles** in the same role (Implementer or Validator). After 3 chained cycles, the 4th week is mandatory non-delivery time: either a **Technical Health Cycle** or unblocked calendar.

**Rationale:**
- The Focus Mandate blocks the Developer's calendar 100% for the cycle. Three consecutive fully-blocked weeks produces measurable fatigue and disconnects the person from the wider team — no standups, no cross-team context, no informal knowledge flow. By week 4 the quality of judgment (exactly what Cronos depends on at its gates) degrades.
- The retros show a structural symptom of unlimited chaining: debt deferred to a "Technical Health Cycle" that never gets scheduled. The frontend E2E gap was flagged in 0001, deferred in 0002, and still open in 0003. The lint backlog (~7 errors) and prettier backlog (~60 files) from 0001 have no landing date.

**Mechanics:**
- The Technical Health Cycle is not optional recovery time that can be traded for another delivery cycle. It is the scheduled owner of the "Tech Health Cycle" rows in every retro's Open Follow-ups table.
- Suggested cadence: 3 delivery cycles → 1 Technical Health Cycle, per person, tracked in the cycle registry.
- Role rotation counts as a partial reset: an Implementer switching to Validator for a cycle resets the chain to 1, since the Validator role is roughly a half-day commitment, not a blocked week.
- The PM enforces this at cycle planning: assigning a 4th consecutive delivery cycle requires an explicit, written, time-bounded exception (same pattern as the Break Glass protocol).

## A2 — Gate 2 (independent Validator) is mandatory at Medium risk and above **[recurred]**

**Evidence:**
- 0001 ran solo on a high-risk tier. Its two riskiest changes (unauthenticated webhook, expanded delete rule) shipped without adversarial testing, and the cost was carried as open follow-ups through cycles 2 and 3. The retro's own Lesson 1: "High-risk cycles need a separate Validator. Period."
- 0002 deliberately held the line ("cycle 2 holds the line") and gated ship on the Validator pass.
- 0009 is the positive proof: Omar's cold-run validation (backend 247 tests, FE 63, grep-verified strictness checks) approved clean, and the retro names Gate 2 as one of the two things that "held under real pressure."

**Rule:** The cycle header must name a Validator ≠ Implementer for any cycle tagged Medium risk or higher. A solo cycle at that tier is a framework deviation requiring written sign-off from the release authority, with a stated compensating control.

## A3 — Fresh-eyes audit step between "tests pass" and "ship"

**Evidence:** 0002's delegated audit (general-purpose agent, explicit file list, 🔴/🟠/🟡/✅ rubric) caught two dormant endpoints, a silent parameter default, and a `Promise.all` partial-save UX hole — all invisible to the author.

**Rule:** Insert an **Audit** step into the Thursday "Rigorous Verification" phase: a fresh agent context (or fresh human) runs the audit rubric against an explicit file list before the Friday demo. Promote `code-audit-rubric.md` from cycle 0002 into `ai-toolkit/prompts/`.

**Counter-rule (same cycle, same evidence):** audit findings are claims, not facts. 0002 spent ~10 minutes "fixing" a stale-race bug that didn't exist. The Implementer must verify each finding against the actual code before acting. Write this into the audit prompt itself.

## A4 — Regression tests must be proven to fail first **[recurred]**

**Evidence:** 0002 encoded two runtime bugs as regression-guard tests and confirmed both assertions fired when the bug was reintroduced. 0009 independently shipped the StrictMode fix with a test "verified to *fail* on the reintroduced bug before being trusted," and promoted the prompt at close.

**Rule:** A regression test that has never been observed failing does not count as a regression guard. The verification record must show the red run. `prove-regression-test-fails-first.md` (already promoted in 0009) becomes framework-level, not toolkit-optional.

## A5 — Narrow-scope formatting as a hard constraint **[recurred]**

**Evidence:** `npm run format` overreach hit 0001 (~60 unrelated files reformatted) and hit 0002 again *despite the written lesson*. The 0002 retro's own diagnosis: "We didn't act on cycle 1's lesson."

**Rule:** Lessons that recur once get mechanized, not re-written. Concretely:
- Add to every `registry/cursorrules/` file: agents run `npx prettier --write <paths-actually-edited>`, never repo-wide format aliases.
- Ship the `narrow-format` skill proposed in 0002.
- Meta-rule for the framework: **any lesson that appears in two consecutive retros must be converted into an enforced rule (cursorrule, CI check, or skill) in the following cycle.** A twice-written lesson is a process bug.

## A6 — Deployment artifacts are release-critical, inside the ship gate

**Evidence:** 0003 was **Held** because Firestore security rules deployment was treated as a post-merge operational task and deferred — leaving a live risk window. Its Lesson 3 says exactly this.

**Rule:** The Friday checklist gains a section: every deployment-adjacent artifact (security rules, IAM grants, bucket lifecycle rules, env config, feature flags) is enumerated in the plan and verified deployed — or explicitly gated — before the release decision is marked Shipped. Note that 0002's unverified `tmp/*` lifecycle rule is the same failure class.

## A7 — Just-in-time endpoint construction (no spec-driven scaffolding)

**Evidence:** 0002 built `patchStatus` and `restoreDefaults` because the SRD listed them, before any UI caller existed. Both were deleted mid-cycle. The retro correctly notes the audit catching this was "luck, not process."

**Rule:** Endpoints, services, and public methods are built when their first caller exists, not when the spec mentions them. Elevate 0002's ADR 4 from project-level to framework-level. This pairs with 0009's Lesson 1 (back-half plan rows are provisional until the rows before them land) — both are the same insight: **the plan authorizes work; it doesn't order it prematurely.**

## A8 — Amendment taxonomy for the plan re-arm gate

**Evidence:** 0009's amendment counter "worked but is blunt": a §13 verification-fix row tripped the re-approval gate as if it were new scope, forcing a needless human round-trip.

**Rule:** Classify each dated plan row as one of:
1. **Material** — new scope, changed design, superseded ADR → re-arms the approval gate (human must re-approve).
2. **Verification-fix** — a fix emerging from the verification phase, within approved scope → logged, no re-arm.
3. **Cosmetic** — wording, typos, formatting → logged, no re-arm.

The Implementer proposes the class; the Validator can contest it. Misclassifying material as cosmetic is a gate violation.

## A9 — Plan size budget

**Evidence:** 0009's plan grew to ~32.5 KB / 22 rows — a real token cost and re-orientation burden for every fresh agent session.

**Rule:** When `01-plan.md` exceeds ~20 KB, the Implementer produces a **plan digest** (≤2 KB: current state, active row, open amendments) that becomes the agent's session-start context, with the full plan as reference. Completed rows collapse to one-line entries with a pointer to the ADR/commit.

## A10 — Retro is a close gate, not an aspiration

**Evidence:** 0004's retro was left as an unfilled template — flagged in 0009's own follow-ups as "the recurring 'retro never gets written' gap." 0003's retro is half-filled (placeholder `- ...` bullets, unfilled ship date). Meanwhile the template itself calls the retro "the most valuable file in the folder for the next Implementer."

**Rule:** A cycle is not closed — and its number is not released for the next cycle — until `05-retro.md` has all three sections (Implementer, Validator, PM) filled, or an explicit "uneventful, nothing to report" entry per role. The `promote-cycle-learnings` step (which 0009 ran successfully) runs only against closed cycles, creating a natural incentive: unwritten retros block promotion of your own wins.

## A11 — Sibling-repo check before external integrations

**Evidence:** 0009: grepping `flow-backend` found a proven jsforce + JWT-bearer integration against the same Salesforce org, reversing a web-research-based design (ADR 5→6) before any code was written.

**Rule:** Before proposing how to integrate with any external system, grep sibling repos for an existing working integration against that same system. Proven in-org code outranks first-principles research. (Prompt already promoted in 0009; this elevates it to a standard plan-phase step for integration cycles.)

---

## A12 — Fourth release-decision state: "Shipped with conditions"

**Evidence:** 0001's footnote: "'Shipped with conditions' would be more accurate." 0009's actual state — shipped to staging, production pending — fits none of the three checkboxes cleanly.

**Rule:** Release decision becomes four states:
- **Shipped** — production, unconditional.
- **Shipped with conditions** — deployed (possibly staging-only); named conditions carried as tracked follow-ups; shipping decision reopens if a condition surfaces a real problem.
- **Held** — with a named unblock condition.
- **Rolled back** — with reason.

## A13 — Reconcile role terminology

The README speaks **Solution Owner / TPO / Developer / Peer Reviewer**; every retro in practice speaks **PM / Implementer / Validator**. Practice has converged on the simpler three-role model, and the gates are named after it (Gate 1 = plan re-arm by PM, Gate 2 = Validator ≠ Implementer). Update the README to the three-role model, mapping TPO responsibilities into the PM role (or into the plan-approval gate explicitly), so the framework docs describe the framework as actually run.

## A14 — Async Daily Pulse (no meeting)

**Problem:** Between the Tuesday Path Sync, the Thursday Checkpoint, and the Friday demo, the Implementer has zero contact with the team. The Focus Mandate designs this in — and it's the same isolation that motivates A1. Today the only mid-cycle visibility the PM has is event-driven (a Reset Trigger firing), which means trouble is visible only after it crosses a threshold: 4+ hours of loop stagnation or 3+ repeated hallucinations.

**Rule:** The Implementer posts a short **async pulse** at the end of each cycle day — no meeting, no call, ~2 minutes to write. Three lines, posted to the team channel (or committed to the cycle folder as `daily/YYYY-MM-DD.md`):

1. **Landed:** what actually reached a working state today (plan row / commit, not intentions).
2. **Next:** the single next step (can reuse the plan's `next_step` field — which also relieves the record-vs-pointer tension 0009 flagged, since the pulse becomes the record and `next_step` stays a pointer).
3. **Friction:** anything looping, ambiguous, or smelling like a Reset Trigger — *before* it hits the mandatory threshold.

**What this is and isn't:**
- It is **not** a standup. No scheduled time, no attendance, no discussion required. Synchronous daily meetings would undo the framework's core trade: Cronos deliberately replaced calendar-driven escalation with event-driven Reset Triggers, and that trade stays.
- It **is** an early-warning input. The PM scans pulses each morning; two consecutive pulses with the same "Friction" line is a soft trigger to check in — catching prompt-loop stagnation from outside before the 4-hour hard trigger fires from inside.
- It **is** a connection mechanism. The team sees daily progress from a person whose calendar is otherwise a black box, which directly mitigates the disconnection cost that A1's chaining limit addresses. A1 caps the damage; A14 reduces the per-cycle dose.

**Cost control:** if the pulse takes more than ~5 minutes to write, it's being over-written. The template enforces brevity (three lines, hard). An uneventful day reads: "Landed: row 6 green. Next: row 7. Friction: none." — that's a complete, valid pulse.

## A15 — Decouple the cycle from the calendar week

**Problem:** The rhythm is currently hard-bound to weekdays — "Monday Initialization," "Tuesday Path Sync," "Friday Midday demo," even the checklist filename (`friday-checklist.md`). This creates artificial constraints: a cycle that's ready to start on a Wednesday either waits idle until Monday or starts misaligned with its own terminology. It also breaks around holidays, PTO, and the A1 Technical Health Cycle, which shouldn't have to consume exactly one calendar week to "reset" the schedule.

**Rule:** The rhythm is defined in **relative days (D1–D5)**, not weekdays. A cycle may start on any working day; D1 is whenever initialization happens.

| Day | Phase | Key activity |
| --- | ----- | ------------ |
| D1 | Initialization | Scaffold project; commit `.cursorrules`; fill PRD template |
| D2 AM | Path Sync | 15–30 min PM + Implementer alignment; zero logic doubts |
| D2–D3 | High-Vibe Execution | "See stuff, say stuff, run stuff" loop with the AI |
| D4 AM | Checkpoint & QA Sync | PM + Implementer review checkpoint; build test suites |
| D4 | Rigorous Verification | Automated tests, security scans, audits (A3) |
| D5 Midday | Demo & Review | Formal demo; Validator runs the survivability checklist |
| D5 PM | Polish & Release | Doc sync; retro (A10); release decision |

**Mechanics:**
- **Weekends and holidays pause the clock.** D-numbers count working days, so a cycle started Thursday runs Thu (D1), Fri (D2), Mon (D3), Tue (D4), Wed (D5). The 72-Hour Modularization Mandate and the Reset Trigger thresholds are already duration-based, so they need no change.
- **Rename calendar-bound artifacts:** `friday-checklist.md` → `d5-checklist.md` (or `release-checklist.md`); retro template's "Filled in Friday afternoon" → "Filled on D5, before the cycle closes."
- **The cycle header records actual dates:** `Started: YYYY-MM-DD (D1)` alongside `Closed:`, so retros and the registry stay auditable against real calendars.
- **Interaction with A1:** the chaining limit counts *cycles*, not weeks — 3 consecutive cycles triggers the break regardless of where they fall on the calendar. This closes a loophole where back-to-back cycles with weekend-straddling starts could chain more intensely than three clean Mon–Fri weeks.
- **Interaction with A14:** the Daily Pulse is posted at the end of each cycle day (D1–D5), unchanged.

**What stays fixed:** the cycle is still exactly 5 working days. Decoupling from weekdays is not license to stretch to 6 or compress to 4 — the deterministic length is the framework's core control, and it survives intact.
